IMPLEMENTED
Incremental balance-transaction discovery reuses the existing two-day overlap, frozen job windows, checkpoint pagination, unresolved dependency retries and protected 085 writers. Empty discovery needs two provider GETs: known LIVE payment binding plus balance list. Recorded balances are skipped only if authoritative principal/expense, required fee evidence and ledger amounts/dates are intact; new refund identities hydrate old parent payments. Late records outside the overlap are caught by separate full verification. No universal guarantee of Stripe event delivery latency is asserted.
Daily full verification scans the complete configured historical scope through a frozen cutoff in seven-day windows. It persists its own job/checkpoint/findings/seen-source evidence. It uses the existing Stripe reader/normalizer, but delegates receipts exclusively to a read-only financial comparison function. No stage/record money writer is callable through daily dispatch. New refunds after the frozen cutoff belong to the next cycle. Missing/unbridged or changed evidence is attention, never invented VAT/costs or automatic historical repair.
The daily trigger starts a cycle. Frequent scheduled ticks may resume an existing cycle only after timely incremental work and within remaining execution budget; they cannot start today's cycle and conceal a missing daily invocation. Manual runs do not resume daily monitoring or emit scheduled pings. A previous day's completed backlog does not certify today's daily cycle. Job watermarks remain independent.

BUDGETS / RECOVERY
Each mode invocation reserves at most 80 reads against a shared rolling 30-day worker budget. Default database cap is 8,000 reads, configured by scan_read_monthly_limit; it is NOT permission to consume other applications' Stripe allocation. Lost measurement responses leave conservative reservations charged. Actual request counts and per-job attribution persist in finance_sync_read_usage; outputs include non-secret request/time metrics. Duplicate measurement is idempotent. Exhaustion produces retry_required, an internal alert and failed monitoring, not a false completed scan.
Stripe requests are serialized with at least 100ms spacing (at most approximately10 worker reads/second). The default scan budget is40 seconds; each HTTP GET timeout is clipped to remaining budget, leaving the60-second route envelope for checkpoint/monitoring/alert overhead. Incremental plus daily continuation share the40-second work allowance. Existing Supabase/network calls can still hit platform timeouts; fencing/checkpoints/idempotency provide recovery, not a promise of uninterrupted latency.
Read allocations are account-wide and transaction-dependent. Before activation, verify the actual account allowance and reserve headroom for Checkout/webhooks. The default worker cap can intentionally stop scanning before month end if history/load exceeds it; it must not be raised without allowance evidence. Daily full-history cost grows with history. The first authorized scan must validate actual read counts, catch-up time, database load and the two-hour daily deadline. Incomplete scans never become verified merely because an HTTP request returned200.

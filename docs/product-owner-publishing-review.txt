AUTHORIZATION
lib/productOwner.ts pins the complete, confirmed ID/email pair on the server.
lib/productOwnerAccess.ts first invokes the existing signed-session and fresh
admin_users gate. It then checks the exact pair and owner role and reads the
current Auth user server-side. Missing/unconfirmed/changed/deleted/banned Auth
identities and lookup errors deny access.
All /api/admin/products POST actions use this gate before body processing:
list, save, sync, publish, review-publish, archive, and unknown actions.
?action=upload-image is gated for both prepare and complete phases.
Authenticated administrators outside this identity receive 403; missing or
invalid admin sessions retain the existing 401 behavior.
The existing HttpOnly/Secure/SameSite=Strict HMAC-signed cookie, expiry,
ADMIN_EMAILS allowlist and other modules' role permissions remain in place.
The actor always comes from the verified session.
No service key, Stripe secret or Auth admin client is imported by the browser.

/api/admin/portal identity adds only canManageProducts, a computed boolean.
AdminPortalShell hides Products when it is false; AdminOverview refuses to mount
the manager without that boolean. The legacy waitlist refresh preserves this
capability only for the same displayed owner identity. These are UI affordances;
the product API independently authorizes every request.

PUBLICATION
ENTWURF SPEICHERN still calls only the existing draft-save RPC. It never invokes
Stripe. Published edits retain their explicit acknowledgement before saving
takes the product out of sale. All 15 field-help disclosure texts remain intact.
CSS, public shop components, checkout, tax and snapshot code were not changed.

The table offers PRUEFEN & VEROEFFENTLICHEN (rendered with German umlauts),
including pending/error drafts. It is disabled while an editor is open to avoid
publishing saved values when the owner is looking at unsaved edits.
The manual Stripe-sync button was removed.

One click calls action review-publish. lib/productPublish.ts:
  1. Reads the exact saved revision and rejects archived/stale products.
  2. Validates product fields, integer gross cents, tax classifications and
     variants with validateProductDraft; requires at least one active variant.
     The existing Metal Case sales restriction remains in force.
  3. Uses synchronizeProduct only if the saved revision is not already synced.
     Existing canonical Product IDs, verified metadata, Price lookup keys,
     provider idempotency keys and accepted-but-lost recovery are reused.
  4. Persists bindings using admin_product_sync_result_v1. A revision-zero
     compatibility product follows the returned revision-one transition.
  5. Re-reads the revision and verifies remote Product/Prices read-only using
     verifyProductStripeMapping, including active state, amount, currency,
     Product ownership, variant metadata and one-time price configuration.
  6. Rechecks owner authorization, invokes admin_product_state_v1, and reads
     the saved revision/status back before returning published:true.
The existing transactional RPCs serialize/check revisions. No new migration is
needed for this implementation. No Price is deleted, archived or repriced.
Legacy sync and publish API actions remain owner-gated for compatibility;
legacy publish retains its existing read-only remote-mapping preflight.

NDJSON progress reports actual server phases:
  Pruefung laeuft
  Stripe wird synchronisiert
  Stripe-Zuordnung wird geprueft
  Veroeffentlichung abgeschlossen
The UI renders the German umlauts, waits for the final published:true result
and a catalog reload, and does not treat an intermediate completion message,
HTTP 200 stream envelope, partial response or disconnected stream as success.
Failures before the publication transaction leave the saved product as draft.
Stripe sync failure is recorded as an error; accepted remote objects remain
recoverable on retry. A stale revision cannot publish a different saved draft.

IMPORTANT RELEASE LIMITATIONS / BLOCKERS FOR REVIEW
1. The literal requirement that EVERY failure returns a product to draft is not
   fully guaranteed across a committed publication and a lost response or
   failed subsequent read/reload. In that situation publication may already be
   committed. The UI reports no success and requests a reload. It does not
   blindly undo a potentially successful concurrent publication. Retrying the
   same saved revision reconciles the existing mappings without duplication.
   This ambiguity must be accepted or the failure requirement revised before
   release. No migration was added to disguise that distributed-systems limit.
2. .env.local has no ADMIN_EMAILS setting. Verify that the existing deployment
   allowlist includes the confirmed full owner email, and perform an owner
   login/access smoke test in a controlled environment before deployment.
   Do not remove the other administrators from the global login allowlist:
   they must retain their other modules. No login configuration was changed.
3. Route tests execute actual TypeScript handlers with mocked infrastructure.
   Publication concurrency checks use a revision-checking in-memory database
   port, not a new real-Postgres stress test. No live owner password/login or
   real Stripe write was used. Hosted streaming/browser behavior remains a
   controlled pre-release smoke check; no deployment was authorized.

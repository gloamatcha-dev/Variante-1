PRODUCT IMAGE STORAGE AND BROWSER OPTIMIZATION — LOCAL RELEASE

User-confirmed Production configuration, project yphubqploumfeabytotc:
  product-images: public, 52428800 bytes (50 MiB)
  product-image-uploads: private, 52428800 bytes (50 MiB)
  Both allow exactly image/jpeg, image/png, image/webp.
  No additional storage.objects policies. No configuration changes were executed.
No new database migration is required. Migrations 001–083 remain unchanged.

The application checks both bucket settings before issuing a signed upload URL.
Bucket capacity is 50 MiB; the independent application limit for an uploaded,
optimized image remains 5242880 bytes (5 MiB). Browser originals up to 50 MiB
are accepted only for local processing. They are never sent to the application
API or Storage. The browser always re-encodes decoded pixels, even small files.

Browser flow:
  Validate source MIME/size/magic; decode with createImageBitmap and explicit
  imageOrientation=from-image. Apply EXIF orientation before measuring dimensions.
  Preserve aspect ratio, never upscale, maximum longest edge 2560 pixels.
  JPEG sources encode as JPEG; PNG/WebP sources encode as WebP with alpha.
  PNG is the lossless fallback if the browser cannot encode WebP.
  Start at quality 0.92, try 0.88/0.84 and smaller dimensions if necessary.
  Accept only a nonempty newly encoded image at most 5 MiB. Reject images above
  100 million decoded pixels. Decode/encode failure never falls back to uploading
  the original. An understandable error leaves the saved image unchanged.
  Show the optimized local preview, upload stage and XHR progress when measurable.
  Revoke preview object URLs and release canvas/bitmap resources.

POST /api/admin/products?action=upload-image accepts only bounded 4 KiB JSON
control messages. Existing fresh owner/admin authorization is required for prepare
and complete. Prepare validates optimized MIME/size and issues a single unique,
actor-scoped private Storage object URL with upsert=false. XHR transfers only the
optimized File directly to that signed URL; no image body crosses a Vercel Function.
No service-role secret reaches the browser. Complete validates actor/path ownership,
downloaded size/MIME, raster signature and complete container boundaries. Invalid,
truncated or appended payloads fail closed. Only validated bytes are promoted to
the public bucket, again without overwriting. Private temporary cleanup is best effort.
Server validation remains authoritative even if browser optimization is bypassed.

No browser INSERT/UPDATE/DELETE policies are required. Private ordinary SELECT/list
must remain denied. Broad inherited/global policies must not grant browser writes
to either bucket. Only server credentials and scoped signed-upload tokens authorize
writes. Real CORS, signed upload, public delivery and policy enforcement remain
release smoke checks: this task does not authorize a Production upload.

The public URL is assigned only to the current editor. Saving remains an unpublished
draft through the existing RPC; uploading never saves, publishes or synchronizes a
product. The existing Shop/PDP reads primary_image_path without a new data model.
Replacement creates a new immutable object. Old images/references are never deleted
or overwritten. Existing Matcha imagery, prices/tax, orders, Stripe and Inventory
remain unchanged. Abandoned uploads may leave an unreferenced public/private object;
automatic cleanup is outside this scope. Public URLs are public even before product
publication; upload only non-sensitive product imagery.
